# Model providers

API settings belong in your local `.env` or environment, never in committed experiment files. `.env.example` contains placeholders. The research harness uses an authenticated Codex CLI; authenticate it with your own account or deployment. The paper research-agent setting is GPT-5.5 with medium reasoning effort.

The research agents use Codex CLI: the meta agent makes data decisions, the executor runs experiments and the analysis subagents inspect evidence. Their model and reasoning effort come from the experiment's `agent` block, and authentication comes from your local Codex configuration.

The data-processing model is called through the shared row-analysis and pool-rewrite operators by the four analysis agents when they need task-local measurements or candidate rewrites; the meta agent decides whether a candidate enters the shared pool or formal training data. These operators are documented under `skills/shared` and are read on demand, rather than automatically injected into every analysis prompt. Independent quality checks and the synthesis batch operator belong to the isolated Synthesis worker; its calls use the recorded batch runner with the synthesis provider. Configure any OpenAI-compatible chat-completions service with `AUTO_SFT_LLM_BASE_URL`, `AUTO_SFT_LLM_MODEL` and `AUTO_SFT_LLM_API_KEY`. Set the URL to the provider's API base, normally including `/v1` (for example, `https://api.example.com/v1` or `http://localhost:8000/v1`), not to a provider-specific SDK URL. The client sends `POST {base_url}/chat/completions` with a Bearer token and a standard `messages` payload. The batch runner retains request bodies, input digests and aligned responses under the run; manifests store an API-key fingerprint. This makes data edits traceable to their inputs and model calls.

Synthesis uses the same recorded batch runner and the same provider as data processing: `AUTO_SFT_LLM_BASE_URL`, `AUTO_SFT_LLM_MODEL` and `AUTO_SFT_LLM_API_KEY`. There is no separate synthesis endpoint. Enable synthesis through the experiment's components list. The paper uses DeepSeek V4 Flash as its generation backend; use the model identifier exposed by your provider. Keep the endpoint and credential in your local `.env`; do not commit the credential.

For a different relay, only the base URL, model identifier and API key need to change. The service must accept OpenAI chat-completions JSON and return either a normal response (`choices[0].message.content`) or an SSE stream with `choices[0].delta.content` followed by `[DONE]`. Provider-specific headers or request fields are intentionally not required; optional reasoning controls are sent only when explicitly configured.

Training and benchmark generation run on your local GPUs and use the active Python by default. Their local HF model paths are independent of these API settings. See [runtime setup](local-runtime.md) for optional interpreter overrides when GPU dependencies conflict.
